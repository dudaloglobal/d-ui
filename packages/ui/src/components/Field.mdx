# Système Field

`Field` porte l'anatomie d'un champ : libellé, aide, erreur, état. Tous les
contrôles de saisie s'y composent, pour qu'aucun n'ait à réinventer son propre
étiquetage.

```tsx
import { Field, FieldDescription, FieldError, Label } from 'd-ui';

<Field required invalid={Boolean(error)}>
  <Label>Adresse e-mail</Label>
  <FieldDescription>Elle sert à la récupération de compte.</FieldDescription>
  <Input type="email" />
  <FieldError>{error}</FieldError>
</Field>;
```

## Câbler un contrôle

`Field` ne connaît pas le contrôle. Celui-ci récupère ses attributs via
`useFieldControl()` :

```tsx
function Input(props) {
  const field = useFieldControl();
  return <input {...field} {...props} />;
}
```

Le hook renvoie `id`, `required`, `disabled`, `aria-invalid` et
`aria-describedby`. Hors d'un `Field`, il renvoie un objet vide — un contrôle
peut donc l'appeler sans condition et rester utilisable seul.

C'est ainsi que `Input`, `Textarea`, `Select` et `Checkbox` se brancheront
(DS-023, DS-024, DS-025), sans que `Field` ait à les connaître.

## Groupes

Un groupe de cases à cocher ou de boutons radio ne peut pas être nommé par un
`label` : `for` ne vise qu'un seul contrôle. `Field group` rend donc un
`fieldset`, et `Label` devient sa `legend`.

```tsx
<Field group required>
  <Label>Notifications</Label>
  <FieldDescription>Choisissez au moins un canal.</FieldDescription>
  <label>
    <input type="checkbox" /> E-mail
  </label>
  <label>
    <input type="checkbox" /> SMS
  </label>
</Field>
```

Dans ce mode, `useFieldControl()` ne renvoie ni `id` ni `aria-describedby` :
c'est le `fieldset` qui les porte. Les poser sur chaque option ferait répéter
l'aide à chaque case.

## Accessibilité

- **`aria-describedby` ne référence que ce qui existe.** `FieldDescription` et
  `FieldError` s'enregistrent auprès du `Field`, et le contrôle ne cite que les
  identifiants réellement rendus. Pointer vers un id absent fait taire l'annonce
  entière chez plusieurs lecteurs d'écran.
- **L'erreur n'est pas dans le DOM tant que le champ est valide.** Un message
  masqué visuellement mais présent reste lu par les technologies d'assistance.
  `FieldError` ne rend `null` que sur `invalid={false}`.
- **`role="alert"` sur l'erreur** : elle est annoncée à son apparition, sans
  attendre que l'utilisateur revienne sur le champ.
- **L'astérisque de champ requis est décoratif** (`aria-hidden`). C'est
  l'attribut `required` du contrôle qui porte l'information. Ajouter en plus un
  texte masqué « requis » ferait annoncer la contrainte deux fois.
- **`aria-invalid` seul ne suffit pas.** L'état invalide est aussi signalé par
  la couleur _et_ par la bordure renforcée, pour ne pas reposer sur la seule
  couleur (WCAG 1.4.1).

## À faire / à éviter

| ✅ À faire                                        | ❌ À éviter                                             |
| ------------------------------------------------- | ------------------------------------------------------- |
| `<Field invalid>` piloté par l'état de validation | Rendre `<FieldError>` en le masquant en CSS             |
| `<Field group>` pour des cases ou des radios      | Un `<Label>` unique pour plusieurs contrôles            |
| `useFieldControl()` dans le contrôle              | Recopier `aria-describedby` à la main dans chaque écran |
| Une `FieldDescription` courte et permanente       | Y mettre le message d'erreur                            |
